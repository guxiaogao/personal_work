## 1. 定位

**增量式动态本体演化引擎 + 最小本体接地问答链路。**

元数据与实例分离，Git 式版本管理（只允许 fast-forward），每次演化由符号推理机自动判定**二维代价等级**并据此决定增量策略。

**不做**：Palantir Foundry 复刻、写回算子（Action）、词汇治理式演化（别名/概念簇）、多模态。

### 1.1 核心主张

> 本体演化的代价可被自动分级，且绝大多数演化是**局部增量**的——把"演化一版 = 重建一次"当常态是对动态本体的根本误解。

引擎要证明的三条断言（可确定性测试，不依赖 LLM）：
1. L0/L1 变更后，存量实例的写入行数 **= 0**
2. L2 变更后，被重解析的实例数 **= SR 反查出的影响集大小**，不多一条
3. L3 变更 **必定被拦截**，且冲突报告能定位到具体违规实例

### 1.2 二维代价模型（本项目自有概念）

`CostTier = (实例代价 I, 检索代价 X)`，各自取 L0–L3。

| SchemaDelta | I | X | 存量实例处理 | 检索索引处理 |
|---|---|---|---|---|
| 新增 EntityType / RelationType | L0 | L0 | 零触碰 | 无（尚无实例） |
| 已有类型加可选属性（无值） | L0 | L0 | 零触碰 | 无（无新值） |
| 加派生属性（惰求值，入索引） | **L0** | **L2** | 零触碰，不写行 | 受影响实例超边重算 + 向量 upsert |
| 加派生属性（惰求值，不入索引） | L0 | L0 | 零触碰 | 无，查询时求值 |
| 属性 parser / datatype 变更 | L2 | L2 | 只重解析影响集 | 对应超边重算 |
| 类型细化为子类型 | L2 | L2 | 影响集重打类型标记 | 超边 key 前缀变化 |
| 删除 / 合并类型 | L3 | L3 | 迁移或标记违规 | 删边 + 重建倒排字典 |
| 约束收紧致存量违规 | L3 | L0 | 标记违规，人工闸门 | 无（值未变） |

派生属性是否入检索索引做成**可配开关**（`attribute_type.index_derived`），MVP 两种都测——这一格是二维模型最有说服力的证据。

**分级判据**
- I 维：影响集是否可由 SR 反查枚举（可枚举 → L2；不可枚举或需迁移 → L3）
- X 维：受影响 hyperedge 集是否可由 `hyperedge.instance_id` 反查枚举
- L0 的额外判据：新版本相对旧版本在**旧签名**上不引入新推论（保守扩展近似判定，见 §5.4）

## 5. 关键设计决策（含实现后的修正）

### 5.1 SchemaRegistry 三条不变式

**fast-forward only**：每个版本单亲，版本图是树。合并仅当目标分支 head 是源分支 head 的祖先。分叉后须基于最新 target 重开提案分支——不做三路合并。

**追加式存储**：类型定义从不 UPDATE。新增 = 插一行带 `introduced_in`；删除 = 写 `removed_in`。"修改"表达为 remove + add 的组合，因此任何历史版本都能重建。

**唯一性不是数据库约束**：同名类型可以合法地出现多次（删除后重新加入，或存在于两个分叉的提案分支上）。唯一性针对"某版本下的可见集"在应用层校验。

可见性 = `introduced_in` 在祖先集内且 `removed_in` 不在。祖先集一次算好再用 `= ANY(...)` 过滤，避免逐行触发递归 CTE。

### 5.2 表结构要点（实际实现）

与初版计划的差异：类型间引用用**名字**而非 id（避免跨版本的 id 纠缠），`schema_version` 无 `is_head` 列（head 由 `branch` 表的指针表达）。

```sql
schema_version(version_id PK, parent_id FK, branch, message, delta_json,
               cost_tier_i, cost_tier_x, created_at)   -- 无 is_head
branch(name PK, head_version_id FK, forked_from FK)    -- head 指针在此

entity_type(id PK, name, uri, parent_name, introduced_in, removed_in)
relation_type(id PK, name, domain_name, range_name, introduced_in, removed_in)
attribute_type(id PK, entity_type_name, name, datatype, min_cardinality,
               derivation_expr NULL, index_derived BOOL, introduced_in, removed_in)
parser_def(id PK, attribute_type_id, kind, pattern, priority,
           not_required, default_value, introduced_in, removed_in)
validator_def(id PK, attribute_type_id, kind, spec_json, introduced_in, removed_in)

instance(id PK, entity_type_name, subject_key, schema_version)
instance_attr(id PK, instance_id, attribute_type_id, value,
              valid_from, valid_to,   -- 有效时间：报告期
              tx_from, tx_to,         -- 事务时间：披露日
              schema_version)
relation_inst(id PK, relation_type_id, src_id, dst_id, valid_from, valid_to, tx_from, tx_to)

conflict_report(id PK, branch, base_version_id, delta_json, cost_tier_i, cost_tier_x,
                violation_count, truncated, status)
conflict_violation(id PK, report_id, kind, entity_type_name, attribute_name,
                   instance_id, subject_key, current_value, constraint_desc)
conflict_type_summary(report_id, entity_type_name, kind, violation_count)  -- 全量聚合
adjudication(id PK, report_id, action, actor, rationale,
             result_version_id, affected_instances)

hyperedge(id PK, instance_id, block_json, schema_version)   -- instance→edge 反查
hypernode(id PK, key_text, value_text)
edge_node(edge_id, node_id)                                 -- 倒排 node→edges
```

辅助函数：`is_ancestor_or_self(anc, desc)`（递归 CTE 上溯）、`visible_at(introduced, removed, v)`。

`instance_attr(attribute_type_id)` 索引**就是 SR 反查影响集的实现**，L2 的"影响集可枚举"靠它成立。

### 5.3 一致性 ≠ 无缺陷（实现后的重要发现）

`isConsistent()` 与"不可满足类"是**两个独立信号**，必须分开报：

```
Weird ⊑ Company ⊓ Filing，而 DisjointClasses(Company, Filing)
⇒ isConsistent() = true    （逻辑上无矛盾）
⇒ Weird 永远不可能有实例   （但这是真缺陷）
```

约束收紧后某个类变成不可满足，恰恰是 L3 该拦的情况，而一致性检查对它返回 true。故 `ConsistencyResult.ok` 要求**两个条件同时满足**。

**推论**：符号校验的可靠性上限取决于 OWL 导出器有没有把矛盾**如实传出去**。曾有一个 bug——同名属性在两个类型上声明了不同 datatype（`Corp.size: number` / `Fund.size: string`），导出器只保留第一个，冲突被静默吞掉，推理机报"一致、无不可满足类"。改成每个 range 都导出后，OWL 的合取语义让 `decimal ⊓ string = ∅`，立刻报出两个不可满足类。推理机再强，拿不到矛盾的公理就什么都发现不了。

### 5.4 保守扩展的近似判定（必须诚实标注）

判定 OWL 2 DL 的保守扩展性在一般情况下**不可判定**（ALCQIO 不可判定；EL 片段为 2ExpTime-complete）。工程上采用**可判定近似**：

1. 取旧签名 Σ = O_i 中出现的类名、属性名、个体名
2. 用 HermiT 对 O_i 与 O_{i+1} 各做一次分类，取原子包含关系与类型断言
3. 将结果投影到 Σ 上做 diff
4. diff 为空 → 判定为"Σ-推论保守"，定 L0；非空 → 输出新增推论清单，降级为 L2/L3

论文与文档中一律表述为 **"有限签名上的演绎保守性近似判定"**，并报告近似误判率（人工核验子集）。主动交代优于被追问。

### 5.5 OWL 导出的两个金融场景默认值

| 开关 | 默认 | 理由 |
|---|---|---|
| `disjoint_siblings` | **关** | 一家公司同时是发行人和投资者是合法的，声明兄弟互斥会大量误报 |
| `include_derived` | **关** | 派生属性无存量值，纳入 minCardinality 约束会误报 |

两者都可显式打开——而这正是 L3 判据要测的场景。父类已被移除时跳过 `SubClassOf`，否则 OWLAPI 会把未声明的父类当成新类，静默改变推理结果。

### 5.6 派生属性表达式边界

语法刻意窄：**纯算术 + 单个时间访问器**。

```
expr   := term (('+' | '-') term)*
term   := factor (('*' | '/') factor)*
factor := ('+' | '-') factor | atom
atom   := NUMBER | IDENT | 'same_period_last_year' '(' IDENT ')' | '(' expr ')'
```

允许 `revenue / same_period_last_year(revenue) - 1`、`(revenue - cost) / revenue`。
不允许跨实例聚合、条件分支、引用其他派生属性、除时间访问器外的任何函数。

三条约束及其收益：

| 约束 | 收益 |
|---|---|
| 无跨实例聚合 | 影响集永远有界（单实例 + 其历史期）。若允许 `sum_over(Company, revenue)`，任一实例变动都让全体派生值失效，L2 退化为 L3 |
| 无条件分支 | 依赖集可**精确**静态分析，不必保守高估 |
| 禁止引用其他派生属性 | 依赖图恒为一层，无需拓扑排序与环检测 |

**手写递归下降解析器**（约 150 行）而非 Python `ast` + 白名单：窄语法比给 Python 语法做减法更可控，不必防 `getattr`、双下划线、推导式等逃逸路径。

`current` 与 `prior` 依赖**分开追踪**：`revenue` 在报告期 P 上变化会让**两个**期的 `revenue_yoy` 失效——期 P 的（经 current 引用）与期 P+1 的（经 prior 引用）。算影响集时两条都要走。

求值用 **Decimal 而非 float**（金额精度）。失败分两类：数据缺失 / 除零 / 非数值 → 返回 null 记日志（新上市公司没有上年同期是常态）；表达式错误 → 抛异常，但正常路径不会发生，因为提交时已校验过。

### 5.7 L3 冲突报告与人工裁决

专利 EP3835968A1 明确**未涉及** validator 失败后的处置动作，此部分自行设计。

**动作三选一**，语义正交：

| 动作 | 语义 | 产出 |
|---|---|---|
| `amend_ontology` | 改本体：放宽约束后重新提交 | 新版本 id |
| `amend_data` | 改数据：给违规实例补值或标记例外，本体不变 | 触碰实例数 |
| `abandon` | 放弃：丢弃提案分支 | 无 |

**理由必填**——"为何这么裁"是审计核心，也是论文里"L3 拦截准确率"的人工核验依据。

**裁决只记录，不执行**：改本体走 `SchemaRegistry.commit`，改数据走 Assimilator。职责分离便于审计，裁决记录与实际变更各有出处。

**明细封顶 200 条，但聚合必须基于全量。** 这是实现时修掉的一个真缺陷：原本 `by_entity_type()` 在被截断的明细上现场聚合，导致 1180 条银行违规显示成封顶值 200、23 条券商违规**彻底消失**。而聚合的目的恰恰是回答"这是否是行业性问题、该不该把约束下推到子类型"——小众类型不可见会让裁决的人漏掉它，下次灌该类型数据时再撞一次同样的冲突。且明细已丢，聚合无法从库里恢复。故 `conflict_type_summary` 独立存表，入库时对全量违规聚合。

### 6.2 关键发现：schema 漂移是横截面自带的

同一个资产负债表接口，不同行业返回的**非空字段集显著不同**——57 个字段位，并集 51，四类共有仅 **22** 个：

| 公司类型 | 非空字段 | 独有字段示例 |
|---|---|---|
| 银行（平安银行 000001） | 32 | `ACCEPT_DEPOSIT` 吸收存款、`LOAN_ADVANCE` 发放贷款、`CASH_DEPOSIT_PBC` 存放央行 |
| 券商（中信证券 600030） | 36 | `AGENT_TRADE_SECURITY` 代理买卖证券款、`BORROW_FUND` 拆入资金 |
| 白酒（茅台 600519） | 31 | `INVENTORY` 存货、`FIXED_ASSET` 固定资产 |
| 保险（中国平安 601318） | 29 | `ADVANCE_PREMIUM` 预收保费 |

**这比"按季度灌入等新概念涌现"强得多**：按行业分批灌入，schema 漂移立刻发生，且是真实业务差异而非人为注入。

三档代价都能用真实数据触发：
- **L0** —— 银行特有字段作为新可选属性加入
- **L2** —— `INVENTORY` 的 parser 在银行语境下需调整
- **L3** —— 给白酒的 `INVENTORY` 加必填约束，再灌银行数据即违规（§5.7 的 CLI 演示就是这个场景）

### 6.3 双时间戳：数据自带，但有一处限制

东财一次调用同时给 `REPORT_DATE`（报告期）与 `NOTICE_DATE`（披露日）。茅台数据里直接撞到追溯调整：

| 报告期 | 披露日 |
|---|---|
| 2026-03-31 | 2026-04-25 |
| **2025-12-31** | **2026-08-15** ← 晚于上一行 |

按报告期排序与按披露日排序**顺序不同**——这就是双时间戳存在的理由。巨潮的预约/实际披露日也真实分离（深振业A 预约 04-29、实际 04-03）。

**限制**：免费接口只返回每个报告期的**最新值**，不给逐字段修正历史；正式报表的 `NOTICE_DATE` 记的是"最近一次涉及该报告期的披露"而非首次（平安银行 2022 年报显示 2024-03-15）。

**绕法**：三级披露链是真实独立的披露事件，各有自己的披露日与值。

| 层级 | 接口 | 特点 |
|---|---|---|
| 业绩预告 | `RPT_PUBLIC_OP_NEWPREDICT` | 给**区间**（`PREDICT_AMT_LOWER/UPPER`） |
| 业绩快报 | `RPT_FCI_PERFORMANCEE` | 确定值，早于正式报数月 |
| 正式报表 | `RPT_DMSK_FN_BALANCE` / `_INCOME` / `_CASHFLOW` | 终值 |

业绩预告给区间、后续收敛为确定值，这本身是另一类漂移（同一属性的值域收窄）。
注意：修正不是每家都有（平安银行 2022 年快报与正式报值一致），要专门筛出有修正的样本。

### 6.4 测试夹具

手写约 50 条，覆盖真实数据里碰不到的边界（约束收紧致存量违规、同名属性 datatype 冲突等）。真实表格跑 parser 链验证机制可用，fixture 保证测试覆盖完整。

## 10. 论文映射（暂不推进，留档）

MVP 完成后，本引擎作为论文 G4 实验臂的实现。差异化对照：

| 对照 | 缺口 | 本项目增量 |
|---|---|---|
| 专利 EP3835968A1 | 明确未涉及 schema 变更后的数据迁移、版本化、已有数据重解析；validator 失败后的处置亦未涉及 | 补上三者，给出形式化代价判据；L3 裁决机制（§5.7） |
| MemGraphRAG（KDD 2026） | 无版本概念、无演化代价模型 | 版本化 + 二维代价分级 |
| OaK（arXiv:2608.22974） | 推理阶段冻结内核，增量更新列为 future work | 增量演化即主题 |
| OG-RAG | 静态本体，增量重建策略未涉及 | 超边增量维护 |

**二维代价模型落在专利与 OG-RAG 的交叉空白里**：专利有本体演化但无检索索引，OG-RAG 有检索索引但本体不演化，只有两者叠加才会暴露"实例代价与检索代价不同步"这一现象（如派生属性 = `(L0, L2)`、约束收紧 = `(L3, L0)`）。

范围外（未来工作）：写回算子、词汇治理式演化、多模态、跨语言 schema 对齐、提案分支的三路合并。
